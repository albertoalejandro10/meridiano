# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

BetoTracker is a personal-finance app (multi-currency accounts, transactions, goals, net worth) built on Nuxt 4 + NuxtHub, UI/UX inspired by Maybe Finance.

## Working in this repo

- **Always use pnpm.** Never npm or yarn. Versions are pinned exact (`.npmrc` sets `save-prefix=""`); when adding deps, list any with postinstall scripts under `pnpm.onlyBuiltDependencies` in `package.json`.
- **Don't test the application as a matter of course.** There is no test suite; don't spin up the app or run curl/smoke checks to "verify" routine edits. Rely on the dev server and TypeScript. Only verify when explicitly asked.
- **Don't run `pnpm build` every time.** It's slow; building is not how you check your work here. Build only when explicitly asked or genuinely needed.
- **UI is bilingual (en + es) via `@nuxtjs/i18n`** — every user-facing string goes through i18n. Keys live in `i18n/locales/en.json` (source of truth) and `es.json` (must mirror keys 1:1; English is the fallback locale). Patterns: `.vue` files use `useI18n()`/`$t()` (data arrays feeding templates become `computed` so they track the locale); Pinia stores and non-component composables use `useNuxtApp().$i18n.t(...)` **at event time** inside action bodies (`useI18n()` throws there); `app/utils/*` hold i18n *keys*, never prose (`accountTypeLabelKey`, `goalIconKeys`, `goalMilestone`, `goalPaceBadge` return keys). Money/date formatting in components goes through `useLocaleFormat()` (shadows the auto-imported utils with locale-aware versions). Strategy is `no_prefix` — no locale in URLs; the choice persists in the `i18n_locale` cookie, picked in Settings → Preferences, with browser-language detection on first visit. `useSeoMeta` titles must be getters (`title: () => t('…')`). **Deferred (still English):** server API `statusMessage`s, Zod messages in `shared/schemas.ts`, seeded default category names, `server/utils/mail.ts`.
- **Never auto-commit.** The owner reviews every change (see the `git-conventions` skill).

## Commands

```bash
docker compose up -d postgres   # local Postgres 18 on port 5433 (NOT 5432)
pnpm dev                        # http://localhost:3000 (auto-applies pending DB migrations)
npx nuxt db generate            # generate a migration after editing server/db/schema.ts
npx nuxt db migrate             # apply migrations to the DB at DATABASE_URL
pnpm build                      # production build (does NOT need a database)
```

Env (`.env`, see `.env.example`): `DATABASE_URL` (Postgres) and `NUXT_SESSION_PASSWORD` (≥32 chars; auto-generated in dev).

## Architecture

**Stack:** Nuxt 4 (`app/` dir) · `@nuxthub/core` · NuxtHub Database = **PostgreSQL via Drizzle ORM** (`postgres-js`) · `nuxt-auth-utils` (email/password) · Nuxt UI v4 · Pinia · Zod 4 · nuxt-charts · date-fns · `@nuxtjs/i18n` (en/es).

### Data layer (Drizzle + NuxtHub)
- Schema is **one file**: `server/db/schema.ts` (tables + enums + `relations()`). Migrations live in `server/db/migrations/postgresql/` and **are committed**. `drizzle.config.ts` is generated by NuxtHub under `.nuxt/` — never create or edit it.
- Server code imports the client as `import { db, schema } from '@nuxthub/db'` (note: it exports `schema`, not `tables`). Relational queries use `db.query.<table>.findMany({ where, with, orderBy })`; for `orderBy` use the **callback form** (`orderBy: (t, { desc }) => [...]`) — externally-built order expressions are unreliable in relational queries.
- **Numeric/date string boundary:** pg `numeric` columns are JS strings in and out, and `date` columns are `'yyyy-MM-dd'` strings (UTC). At write time convert with `toAmount(n)` / `toDateStr(d)` from `server/utils/serialize.ts` (auto-imported). At read time, `Number(...)` the numeric strings.
- **Balances are derived, never stored** (SQL aggregation in `accounts/index.get.ts`). Asset accounts: balance = `initialBalance + Σ(INCOME) − Σ(EXPENSE)`. **Liability accounts store a positive "amount owed"** with the mirrored formula (`initialBalance + Σ(EXPENSE) − Σ(INCOME)`): charges are EXPENSE (debt grows), payments arrive as the INCOME leg of a transfer (debt shrinks). Net worth = Σ assets − Σ liabilities, **computed per currency — amounts in different currencies are never summed** (no FX rates; see `sumByCurrency` in `app/utils/index.ts`).

### Auth & request scoping
- `nuxt-auth-utils` sealed-cookie sessions. `server/api/auth/{register,login,logout}` hash/verify passwords and call `setUserSession`/`clearUserSession`. The session `User` type is augmented in `shared/auth.d.ts` (`#auth-utils` — it lives under `shared/` so both the app and server tsconfigs pick it up).
- `server/middleware/auth.ts` runs for `/api/v1/*`: it resolves the session and sets `event.context.userId` (else 401). **Every `/api/v1` handler reads `event.context.userId` and scopes all queries/mutations by it** — there is no SQL-level RLS; ownership is enforced in application code. Mutations validate bodies with Zod schemas from `shared/schemas.ts`.
- **Password reset:** `server/api/auth/password/{request,reset}` issue and consume single-use SHA-256-hashed tokens (`password_reset_tokens` table, 1h expiry). Reset links are built from `runtimeConfig.public.siteUrl` (`NUXT_PUBLIC_SITE_URL`, required in production — never from the request Host header). Email delivery is stubbed in `server/utils/mail.ts` (logs the reset link) until an email provider is wired in. Known limitation: sealed-cookie sessions can't be revoked server-side, so a password reset does not log out existing sessions.
- New users are seeded with a starter set of categories on register (`server/utils/defaultCategories.ts`).

### Frontend data flow
- Pages/components never query the DB directly — they go through composables (`useAccounts`, `useTransactions`, `useGoals`, `useTransfers`) that hit `/api/v1/*` via `useFetch`/`$fetch`. `useTransactions` derives its `useFetch` key from the active filters (never share one key across different queries). Transaction/transfer mutations call `refreshNuxtData()` (no args) so every loaded list — derived balances included — refetches.
- Auth state on the client comes from `useUserSession()` (wrapped by `app/stores/session.ts`).
- Component naming is Nuxt-default: folder = prefix, file = suffix (`account/Modal.vue` → `<AccountModal>`, `transfer/Modal.vue` → `<TransferModal>`). Globally-registered overlays live in `app/components/global/`.

### Account types (asset/liability)
Account types are defined in **four places that must stay in sync** when adding/removing one: the `account_type` pg enum in `server/db/schema.ts`, `accountTypes` + `accountTypeGroups` in `shared/schemas.ts`, the `accountTypeMeta` catalog (icon/group) in `app/utils/accounts.ts`, and the `accountTypes.<TYPE>` label block in **both** `i18n/locales/en.json` and `es.json`. The UI derives the asset/liability split, icons, labels, and the "what to add" picker from these — so a new type flows through the forms and dashboard automatically once all four are updated (then `nuxt db generate` for the enum change).

### Transfers & selling assets
A transfer is a **linked pair of transactions** (one `EXPENSE` on the source + one `INCOME` on the destination) sharing a `transferId`, so per-account balance math is unchanged. Transfers are **excluded from goal savings** (`transferId IS NULL` filter in `goals/index.get.ts`) and are surfaced in the transaction list with their counterpart account. "Sell asset" (`POST /api/v1/accounts/:id/sell`) is a transfer of the sale proceeds into a cash account plus archiving the asset; the realized gain/loss is implicit in the net-worth change. Deleting either leg of a transfer deletes both.

**Fees** (optional on transfers, transactions, and sales) are separate `EXPENSE` rows in the "Fees" category, linked to their parent via the `feeOfId` self-FK (cascade delete) with `transferId` kept NULL — so they count as real expenses in goal pace and reduce balances automatically. Transfer/sale fees land on the **receiving** account (destination nets `amount − fee`); a transaction's fee lands on its own account. Percent entry is UI-only sugar (`<FeeInput>`) — the API stores fixed amounts. `ensureFeesCategory` (`server/utils/categories.ts`) lazily creates the category for users who predate it.
